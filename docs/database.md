# Database

PostgreSQL, hosted on **Supabase**. The backend connects with the
**service-role key** (`SUPABASE_SERVICE_ROLE_KEY`) and is the only client that
writes data.

- **Canonical schema:** `database/schema.sql` (the full, current shape — used for
  fresh installs).
- **Migrations:** `database/migrations/*.sql` (dated, incremental changes applied
  to existing databases).

## Applying schema, migrations, and seed

The backend has a single database pipeline command. It applies:

1. `database/schema.sql`
2. every dated SQL file in `database/migrations/` in filename order
3. `database/seed.sql`

`database/migrations/000-apply-all.sql` is skipped because it is a bundle of
dated migrations, not a separate migration step.

Set a raw Postgres connection string in `backend/.env`:

```bash
SUPABASE_DB_URL=postgresql://...
```

Then run:

```bash
npm run db:pipeline
```

To inspect the exact order before applying SQL:

```bash
npm run db:pipeline -- --dry-run
```

To include demo content after the normal seed:

```bash
npm run db:pipeline -- --demo
```

All migrations are idempotent (`create table if not exists`, `add column if not
exists`), so re-running is safe.

## Table groups

### Content (admin CMS → public site)
`tours`, `tour_inclusions`, `tour_exclusions`, `tour_images`, `itinerary_days`,
`pricing_options`, `available_dates`, `tour_categories`, `destinations`,
`countries`, `lodges`, `activities`, `trip_points`, `safety_topics`,
`travel_styles`, `comparisons`, `blog_posts`, `blog_categories`,
`gallery_images`, `testimonials`, `faqs`, `media_library`, `website_settings`
(homepage sections, branding, feature flags).

Most content tables share conventions: `id uuid`, `slug`, a `status`
(`draft`/`published`/`archived`), `created_at`/`updated_at`, and a soft-delete
`deleted_at`.

### Bookings, leads & the trip portal
| Table | Purpose |
|-------|---------|
| `booking_requests` | The lead/booking store. `booking_code` (unique), traveller details, `status`, `payment_status`, `lead_context` (jsonb brief), `source`. **No separate customer-accounts table** |
| `booking_payments` | Payments recorded against a booking (`booking_id`) |
| `contact_messages` | Contact-form messages **and** trip-portal messages (tagged `Trip portal · <code>`) |
| `trip_access_tokens` | Magic-link tokens — stores only the **SHA-256 hash**, with `expires_at`, `revoked_at`, `last_used_at`. See [features.md](features.md#trip-portal-magic-link) |

### Media
`media_library` — uploaded files. Each image also gets a `thumbnail_url` /
`thumbnail_path` (a 600px webp generated by `sharp` on upload). See
[features.md](features.md#media-library--thumbnails).

### Admin & access control
`admin_users`, roles & permissions (used by `requirePermission`), `audit_logs`
(before/after diffs for admin actions).

### AI advisor
`ai_*` — conversations, messages, usage/cost tracking, `ai_answer_cache`
(semantic cache) and `cms_embeddings` (pgvector). Anonymous data is purged after
`AI_DATA_RETENTION_DAYS`.

### Analytics
`analytics_events` — first-party, **PII-free** event stream (event name,
anonymous `session_id`, page, optional tour ref). Purged after
`ANALYTICS_RETENTION_DAYS`. Personal data stays in `booking_requests`.

## Generic data access

CRUD for most resources goes through `backend/src/utils/supabase-helpers.ts`
(`listRecords`, `getRecordBySlug`, `getRecordById`, `createRecord`,
`updateRecord`, `softDeleteRecord`). These also:

- enforce soft-delete (`deleted_at is null`) on reads,
- write `audit_logs` on create/update/delete,
- attach `<column>_thumbnail` for image columns on public reads (so cards load webp thumbnails).
